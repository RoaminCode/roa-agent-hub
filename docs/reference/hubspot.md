# HubSpot: access, Delivery records, data and dates

What the hub may read and write in HubSpot, how Delivery records are made, and which fields mean what. Read before touching `src/hubspot/`.

## Access (private app for the hub)
- Read: `crm.objects.contacts.read`, `crm.objects.deals.read`, `crm.objects.owners.read`, `crm.objects.custom.read` (Delivery, LS Deals, Repair Orders, Units), `crm.schemas.deals.read`, `crm.schemas.custom.read`, `sales-email-read` (one-to-one email bodies), and the call transcript read scope if listed separately.
- Write, for notes only: notes are engagements, which HubSpot gates behind `crm.objects.contacts.write` (and possibly `crm.objects.deals.write` and `crm.objects.custom.write` to attach a note to a deal or Delivery). HubSpot cannot narrow these to notes, so the no-field-edits rule is enforced in hub code. The HubSpot client's only writes are four narrow methods in `src/hubspot/client.js`: `createNote` (a note on the Roamer and the Delivery record, never on a deal), `updateNote` (PATCH a note only after reading it and confirming it is Basecamp's own), `createDelivery`, and `linkNoteToDelivery`. `post()` still refuses anything but search and batch read, and `test/hubspot.test.js` fails if any other write appears.
- Scopes on the key, read from HubSpot 2026-11-06 (held since it was created 2026-10-28): the read scopes above plus `crm.extensions_calling_transcripts.read`, `conversations.read`, `conversations.custom_channels.read`; writes `crm.objects.contacts.write`, `crm.objects.deals.write`, `crm.objects.custom.write`, `conversations.write`, `conversations.custom_channels.write`. Token in Secret Manager as `hubspot-access-token`, readable only by `basecamp-router` (rotated once; version 1 destroyed).
- The conversations write scopes stay on the key until Blake decides they are not needed. No hub code uses them. Known risk: posting a message to an Aloware SMS thread through the HubSpot conversations API only stores it; it is never delivered, and it leaves a false "sent" record (tested 2026-10-28). Texts sent from HubSpot are actually sent by Aloware's app, which then writes the copy into HubSpot.

## Delivery records
- Basecamp owns creating and linking Delivery records (Blake's call, 2026-11-07). When a deal space opens ("open a space" or "use this space"), Basecamp uses the deal's Delivery record if it has one, else creates one in the Delivery Pipeline at Deposit Received with its Name and Trailer and nothing else filled, and links it to the deal (association type 98) and the Roamer (96). Notes link to it with type 95. One record per deal: the database records it, the same way as spaces. The RJB Agent Spec's "creates the Delivery record when a Deal enters Deals" is replaced by this. Built 2026-11-07 (`src/hubspot/deliveries.js`, `createDelivery` and `linkNoteToDelivery` in the client); live and verified 2026-11-07 on 51455 (record created at Deposit Received, named, linked to the deal and the Roamer, brief note on it): since `basecamp-00048-6hn` it runs before the brief is posted (so a new brief note is created on the record, and the card links to it); the brief card's buttons are Open deal, Open Roamer, and Open Delivery (Blake, 2026-11-07), the last once the deal has a Delivery record; runs after the brief is posted in "open a space" and "use this space"; links the deal's brief note to the record; later space notes and Q&A notes are created on it too. A failure is logged ("could not find or create Delivery record") and the space stays open. Title fields (Blake, 2026-11-07): the record's title is `delivery_name` ("Name", "51455 - Pat Sample") and the line under it `delivery_trailer` ("Trailer"), both filled once from the deal name at creation. The delivery date stays on the Deal, where LightSpeed keeps it true; the Delivery object keeps no date of its own. `delivery_date` was the title and a required field; its required flag was cleared 2026-11-07 through the schema API (HubSpot's settings do not offer it), with `crm.schemas.custom.write` added to the key for that one change and removed the same day.
- The Delivery object has 17 custom fields (rebuilt 2026-11-08): accessibility_notes, camp_style, delivery_attendees, delivery_coach, delivery_name, delivery_trailer, experience_level, first_planned_trip, open_questions, profile_confirmed_by, profile_confirmed_on, promises_to_honor, roamer_concerns, roamer_excitement, roamer_story, service_advisor, time_slot. The 23 earlier fields are archived (restorable in HubSpot). The "Delivery Coach Assigned" tag filters on `delivery_coach`.

## Data and dates
- Trailer arrival: a 17-character VIN in the deal's `ls_unit_vin` means the trailer is on the lot and in inventory (Blake, 2026-11-08); empty means not yet.
- `projected_delivery_date` drives everything before delivery; `ls_delivery_date` marks the trailer leaving the lot and closes the record at Finalized.
- Mods come from LightSpeed labor lines: Dealer Add, Customer Add, and "(Charge sales)" Prep lines (included at no charge). Prep lines are the PDI and its findings. Install status is per repair order only in the deal feed.
- Parts quantity fields (Requested vs Qty, I vs S) are not understood yet; parts questions go to people.
- Calls carry `hs_call_has_transcript` and `hs_call_transcription_id`, but every transcript endpoint returns 404; briefs read `hs_call_summary` and the Aloware summary in `hs_call_body`.
- HubSpot holds texts in three formats, all read: Aloware's "<sender> has sent an SMS ... Message:" header, the conversations inbox header with no "Message:" line, and a "Name (Rvs of America):" line then the message. A sender the record does not show stays unknown rather than guessed.
